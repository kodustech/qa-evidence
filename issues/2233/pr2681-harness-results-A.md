## X7: chat question lost on a 24k window (follow-up to the S8 QA finding)

**Verdict: fail. Reproduced at merge, absent at the first parent.** On a 24k slot with no `maxOutputTokens`, every request the conversation agent sends drops the developer's question. The cut already happens on step 1, before any tool runs: the PR diff is not needed to trigger it. The first parent keeps the question but sends 99k-token requests on 24k (the overflow #2233 is about).

**Harness:** `harness/A/s8x-chat-question.ts`. It runs on the real `AiSdkAgentRunner` and uses the real `buildSystemPrompt`, the real `buildUserPrompt` with the thread context the chat use case passes (PR description, original Kody suggestion with its diff hunk), the real `buildDecisionTool`, `AiSdkToolRegistry` and `conversationCompression`. The only stub is the model. Steps: (1) the model calls `KODUS_GET_PULL_REQUEST_DIFF`, which returns a 171,181-char diff (a 60k SVG path line, a 30k minified JSON line, an 80k hex line, and 4 small TS files: 95,775 tokens); (2) the model calls `kodusDecideAction`; (3) it answers. The PR description is the one Kody's PR summary writes into the PR, about 8.8k chars, as on QA PR-A after R1.

On the failing run, the first user message reaches the model as 547 chars ending `…the fee brea…[truncated]`. `USER MESSAGE: @kody …` is gone, so the model sees only PR context with no question. That matches the QA replies ("came through truncated", "What would you like done with this PR?").

**Mechanism**
1. The conversation reserves its own 20,000-token answer when the slot sets no `maxOutputTokens`. The value is `maxOutputTokensFallback = 20000` at `conversationAgent.ts:115`, passed at `:268`, and used as `answerTokens` at `conversation-window.ts:35`. On a 24k window that leaves `room = 4,000`. The safety margin is 8% of the window plus `(window - room)`, which is 1,920 + 20,000 = 21,920 (`conversation-window.ts:44-46`). The message budget is then 24,000 - 382 (estimated overhead) - 21,920 = **1,698 tokens**.
2. The first user message is built by `buildUserPrompt`. It puts the PR description, the original suggestion and the identifiers first, and the developer's text last (`conversation-prompt.ts:159`, `'USER MESSAGE:'`, then `prompt`). With Kody's summary in the PR description, that message is 2,086 tokens, larger than the 1,698 budget on its own.
3. `ContextWindowCompressor.maybeCompress` is over budget and calls `clampMessagesToBudget` (`context-window-compressor.ts:140`). Phases 1 and 2 shrink tool results and evict old rounds but never touch the head. Phase 3, `hardTruncateToFit` (`context-compressor.ts:642` → `:588`), applies `truncateToolMessage` to **every** message, the head user message included. That keeps the start of each text (`text.slice(0, maxChars)`, `context-compressor.ts:260`) and halves the cap until the window fits. The tail of the first user message, which holds the question, is what gets cut.
4. A secondary undercount makes the real requests larger than the compressor believes. The overhead estimate counts the tools through `AiSdkToolRegistry` views, whose schema is empty by design (`ai-sdk-tool-registry.ts:61`). Here it estimated 382 tokens where the real system + tools sent are about 638. With the real MCP tool set on QA the gap is larger. This is consistent with the QA span: 28,730 input tokens summed over the steps, most of it cached tools.

**Why the controls pass:** with a 1M window, or with the slot's own `maxOutputTokens: 4000` on 24k, the budget is far above the 2,086-token head. With a short description, the head (324 tokens) fits in 1,698. The failure needs a small window, no slot `maxOutputTokens` (so 20k of 24k goes to the answer), and a first user message above about 1.7k tokens. Kody's own PR summary in the description is enough for that.

**Mutant/control:** the controls above serve as the comparison. `onlyWhenOverBudget` has no effect here, because the clamp runs on the over-budget path.
